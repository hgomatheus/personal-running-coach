# Requirements Document

## Introduction

A personal running training application designed for two-profile, local-network use on a Raspberry Pi via Docker. The app provides a feature-rich training experience comparable to premium apps like Runna, including AI-generated personalized training plans, Strava integration for workout sync, detailed running history, and structured coaching workflows. No authentication is required since the app is accessible only over the home WiFi network. The app supports exactly two independent user profiles, each with their own training data, Strava connection, and preferences. All distances are stored and displayed exclusively in kilometres.

## Glossary

- **App**: The personal running coach web application running in Docker on the Raspberry Pi.
- **User**: One of the two people using the app on their home network.
- **Profile**: One of the two independent user profiles supported by the App. Each Profile has its own runner data, training plan, run history, Strava connection, pace zones, HR zones, statistics, streaks, personal records, and notification settings.
- **Active_Profile**: The Profile currently selected on the Dashboard via the profile switcher.
- **Training_Plan**: A structured, multi-week schedule of running workouts generated by the AI coach for a specific Profile.
- **Workout**: A single scheduled or completed running session with defined type, distance, pace, and estimated duration targets.
- **WorkoutStep**: A single step within a Workout (e.g., warm-up, interval, cool-down). Each step's primary target is `distance_metres`; estimated duration is derived from distance ÷ pace zone.
- **Run**: A completed workout activity, either synced from Strava or logged manually, belonging to a specific Profile.
- **AI_Coach**: The AI component responsible for generating and adapting training plans.
- **Strava**: The third-party fitness tracking platform used to sync completed runs.
- **Strava_Sync**: The process of importing completed activities from Strava into the App for a specific Profile.
- **Dashboard**: The main overview screen showing the Active_Profile's current plan progress, upcoming workouts, and recent activity.
- **Training_Block**: A themed phase within a Training_Plan (e.g., base building, speed work, taper).
- **Pace_Zone**: A defined running intensity range expressed in minutes per kilometre.
- **Heart_Rate_Zone**: A defined cardiovascular intensity range expressed as a percentage of maximum heart rate.
- **Race_Goal**: A target race event (distance and date) that anchors the Training_Plan.
- **Weekly_Mileage**: The total distance run in km across all Runs in a calendar week for a given Profile.
- **Streak**: A consecutive sequence of weeks in which the User completed all scheduled Workouts.
- **RPE**: Rate of Perceived Exertion — a subjective 1–10 scale for workout difficulty.
- **Docker_Container**: The isolated runtime environment hosting the App on the Raspberry Pi.
- **Local_Network**: The home WiFi network through which the User accesses the App.
- **FIT_File**: A binary file in the Flexible and Interoperable Data Transfer (FIT) protocol format, used by Garmin devices to represent structured workouts.
- **FIT_Exporter**: The backend service responsible for generating FIT_Files from Workout records.
- **Garmin_Device**: The user's Garmin Forerunner 970 GPS watch onto which structured workouts are loaded.
- **Repeat_Step**: A FIT workout step that encodes an interval repeat block, referencing a starting wkt_step_index and a repeat count.
- **Post_Run_Analysis**: A screen showing a side-by-side comparison of a matched Run's actual metrics against the scheduled Workout's targets, including an AI-generated coaching summary.
- **Weather_Advisory**: A text note appended to a Workout coaching note when forecast conditions (temperature, humidity, wind, or rain) may affect performance.
- **Open_Meteo**: The free, no-API-key weather forecast service used to retrieve forecasts for workout days.
- **Race_Countdown**: A Dashboard widget showing the number of days remaining until the Active_Profile's Race_Goal date, displayed only when an active Race_Goal exists.
- **RouteRecord**: A stored GPS polyline extracted from a Strava-synced Run, used to generate route suggestions for Workouts.
- **Taper_Phase**: The final weeks of a Training_Plan before a Race_Goal, characterised by reduced training volume and maintained intensity to allow the body to recover and peak for race day.
- **Taper_Training_Block**: The final Training_Block in a Training_Plan that covers the Taper_Phase period.

## Requirements

### Requirement 1: Local-Network Access Without Authentication

**User Story:** As a user, I want to open the app in any browser on my home network without logging in, so that I can access my training data instantly.

#### Acceptance Criteria

1. THE App SHALL be accessible via a browser on the Local_Network without requiring a username or password.
2. WHEN a request arrives from outside the Local_Network, THE App SHALL reject the connection with an HTTP 403 response.
3. THE App SHALL bind exclusively to the local network interface and SHALL NOT expose any port to the public internet.
4. THE Docker_Container SHALL restart automatically after a Raspberry Pi reboot without manual intervention.

---

### Requirement 2: Onboarding and Runner Profile

**User Story:** As a user, I want to set up my runner profile with my current fitness level and goals, so that the AI Coach can build a plan tailored to me.

#### Acceptance Criteria

1. WHEN the App is launched for the first time for a given Profile, THE App SHALL present an onboarding flow to collect runner profile data for that Profile.
2. THE App SHALL collect the following profile fields: date of birth, biological sex, current weekly mileage in km (optional if a Strava bulk import is provided for this Profile), longest recent run distance in km (optional if a Strava bulk import is provided for this Profile), and any injury history notes. All distances are stored and displayed exclusively in kilometres.
3. THE App SHALL collect at least one Race_Goal consisting of a race distance in km and a target race date.
4. WHEN the User submits the onboarding form with all required fields, THE App SHALL persist the profile for the Active_Profile and proceed to Training_Plan generation.
5. IF a required profile field is missing, THEN THE App SHALL highlight the missing field and prevent form submission.
6. WHEN the User updates the runner profile after onboarding, THE App SHALL prompt the User to regenerate the Training_Plan for the Active_Profile.

---

### Requirement 3: AI-Generated Personalized Training Plan

**User Story:** As a user, I want the AI Coach to generate a structured multi-week training plan based on my profile and race goal, so that I follow a scientifically sound progression toward my target race.

#### Acceptance Criteria

1. WHEN the User completes onboarding or requests a new plan, THE AI_Coach SHALL generate a Training_Plan for the Active_Profile that spans from the current date to the Race_Goal date.
2. THE AI_Coach SHALL structure the Training_Plan into named Training_Blocks (e.g., Base Building, Threshold Development, Race Preparation, Taper).
3. THE AI_Coach SHALL schedule no more than one quality Workout (interval, tempo, hills, or long run) per day.
4. THE AI_Coach SHALL include at least one rest day or easy recovery day per week in the Training_Plan.
5. THE AI_Coach SHALL use only the following Workout types when generating a Training_Plan: **Easy Run** (low intensity, conversational pace, easy zone), **Tempo** (sustained effort at threshold pace zone), **Intervals** (repeated high-intensity efforts with recovery steps, e.g. 6 × 400 m), **Hills** (repeated hill repeats with recovery jog back down), **Long Run** (extended easy/moderate effort, the week's longest run), **Race** (race-day workout type, used when the User runs an actual race), **Rest** (full rest day), and **Recovery** (very easy active recovery). THE AI_Coach SHALL NOT generate Workouts of any other type.
6. THE AI_Coach SHALL calculate target Pace_Zones for each Workout based on the Active_Profile's current fitness data and Race_Goal.
7. WHEN the Active_Profile's recent Run data indicates a fitness change of more than 5% from the baseline, THE AI_Coach SHALL offer to recalculate Pace_Zones for that Profile.
8. THE App SHALL display the full Training_Plan as a scrollable weekly calendar view.
9. THE App SHALL display each Workout with its type, target distance in km, and target Pace_Zone; estimated duration SHALL be shown as a secondary, derived value only — calculated from target distance divided by the target Pace_Zone velocity.
10. WHEN the AI_Coach generates a Training_Plan, THE App SHALL complete generation within 30 seconds.

---

### Requirement 4: Adaptive Plan Adjustment

**User Story:** As a user, I want the training plan to adapt when I miss workouts or my fitness changes, so that the plan stays realistic and effective.

#### Acceptance Criteria

1. WHEN the User marks a Workout as skipped, THE AI_Coach SHALL recalculate the remaining Training_Plan for the Active_Profile to redistribute training load.
2. WHEN the User completes a Run that deviates more than 20% from the scheduled Workout distance in km, THE AI_Coach SHALL adjust the following week's training load accordingly.
3. THE App SHALL allow the User to manually request a plan regeneration at any time.
4. WHEN the User reports an injury via the profile, THE AI_Coach SHALL reduce training load and remove high-intensity Workouts for a configurable recovery period.
5. THE AI_Coach SHALL preserve the Race_Goal date during plan adjustments unless the User explicitly changes it.
6. THE App SHALL provide a "Reset Plan" button on the Training Plan screen for the Active_Profile.
7. WHEN the User clicks "Reset Plan", THE App SHALL display a confirmation dialog with the text "This will permanently delete your current training plan and all scheduled workouts. This cannot be undone. Are you sure?" and two options: "Cancel" and "Reset Plan".
8. WHEN the User confirms the reset, THE App SHALL delete the active Training_Plan and all associated Workouts and Training_Blocks for the Active_Profile, then redirect the User to the plan creation flow.
9. WHEN the User cancels the reset dialog, THE App SHALL dismiss the dialog and make no changes.
10. THE reset action SHALL NOT delete any completed Run records or historical data for the Active_Profile.

### Requirement 5: Workout Detail and Structured Sessions

**User Story:** As a user, I want detailed, structured workout instructions for each session, so that I know exactly what to run and at what effort.

#### Acceptance Criteria

1. WHEN the User opens a Workout, THE App SHALL display a step-by-step session structure (e.g., warm-up, main set intervals, cool-down) where each WorkoutStep shows its distance in km and Pace_Zone; `distance_metres` is the primary target field for each WorkoutStep. THE App SHALL support and display the following Workout types with appropriate structure: **Easy Run** (single continuous step at easy zone), **Tempo** (warm-up, sustained tempo step, cool-down), **Intervals** (warm-up, repeated interval + recovery steps, cool-down), **Hills** (warm-up, repeated hill repeat + recovery jog steps, cool-down), **Long Run** (single continuous step at easy/moderate zone), **Race** (race-day session with warm-up and race step), **Rest** (no steps — rest day indicator only), and **Recovery** (single easy step).
2. THE App SHALL display the target Heart_Rate_Zone for each WorkoutStep where applicable.
3. THE App SHALL display a plain-language coaching note for each Workout explaining the purpose and execution tips.
4. THE App SHALL display the total target distance in km for each Workout; estimated total duration SHALL be shown as a secondary, derived value calculated from total target distance divided by the target Pace_Zone velocity.
5. WHEN the User completes a Workout, THE App SHALL prompt the User to log an RPE score between 1 and 10.
6. IF the User logs an RPE score above 8 for two consecutive Workouts of the same type, THEN THE AI_Coach SHALL reduce the intensity of the next Workout of that type.

### Requirement 6: Strava Integration — Activity Sync

**User Story:** As a user, I want my completed runs from Strava to sync automatically into the app, so that my training history is always up to date without manual entry.

#### Acceptance Criteria

1. THE App SHALL support OAuth 2.0 authorisation with Strava so each Profile can independently connect its own Strava account from the settings screen.
2. WHEN a Profile connects its Strava account, THE App SHALL import all running activities from the past 90 days for that Profile only.
3. THE App SHALL poll the Strava API for new activities for each connected Profile at a configurable interval, with a default of every 15 minutes.
4. WHEN a new Strava activity of type "Run" is detected for a Profile, THE App SHALL import it as a Run for that Profile and attempt to match it to a scheduled Workout in that Profile's Training_Plan.
5. WHEN a Strava Run is matched to a scheduled Workout, THE App SHALL mark that Workout as completed and display the actual vs. target metrics in km.
6. IF the Strava API returns an error for a Profile's sync, THEN THE App SHALL log the error, display a sync status indicator to the User, and retry after the next configured interval.
7. THE App SHALL display the last successful Strava_Sync timestamp for the Active_Profile on the settings screen.
8. WHEN the User disconnects a Profile's Strava account, THE App SHALL revoke the stored OAuth token for that Profile and retain all previously imported Run data for that Profile.

### Requirement 7: Manual Run Logging

**User Story:** As a user, I want to log a run manually when I don't use Strava, so that my training history remains complete.

#### Acceptance Criteria

1. THE App SHALL provide a manual run entry form accepting: date, distance in km, duration, average heart rate (optional), and notes (optional).
2. WHEN the User submits a manual Run entry, THE App SHALL validate that distance is greater than 0 km and duration is greater than 0 before saving.
3. IF the User submits a manual Run entry with invalid data, THEN THE App SHALL display a field-level error message and prevent saving.
4. WHEN a manual Run is saved, THE App SHALL attempt to match it to a scheduled Workout on the same date in the Active_Profile's Training_Plan.
5. THE App SHALL allow the User to edit or delete any manually logged Run belonging to the Active_Profile.

### Requirement 8: Running History and Statistics

**User Story:** As a user, I want to view my complete running history and key statistics, so that I can track my long-term progress.

#### Acceptance Criteria

1. THE App SHALL maintain a chronological log of all Runs (both Strava-synced and manually logged) for the Active_Profile.
2. THE App SHALL display per-run metrics: date, distance in km, duration, average pace in min/km, average heart rate (where available), and elevation gain in metres (where available).
3. THE App SHALL display Weekly_Mileage totals in km for each calendar week in a bar chart.
4. THE App SHALL display a monthly summary showing total distance in km, total duration, and number of Runs.
5. THE App SHALL display the Active_Profile's current Streak and longest-ever Streak.
6. THE App SHALL display personal records for the following distances: 1 km, 5 km, 10 km, half marathon, and marathon.
7. WHEN a Run sets a new personal record for any tracked distance, THE App SHALL highlight the achievement on the run detail screen.
8. THE App SHALL allow the User to filter the run history by date range, run type, and distance range in km.

### Requirement 9: Dashboard and Progress Overview

**User Story:** As a user, I want a dashboard that shows my current plan status and upcoming workouts at a glance, so that I always know what to do next.

#### Acceptance Criteria

1. THE Dashboard SHALL display a profile switcher allowing the User to select which of the two Profiles is the Active_Profile; no login is required.
2. THE Dashboard SHALL display the next scheduled Workout for the Active_Profile with its type, target distance in km, and target Pace_Zone.
3. THE Dashboard SHALL display the current Training_Block name and the number of weeks remaining until the Active_Profile's Race_Goal.
4. THE Dashboard SHALL display the current week's planned vs. completed mileage in km as a progress bar for the Active_Profile.
5. THE Dashboard SHALL display the Active_Profile's Streak.
6. THE Dashboard SHALL display the three most recently completed Runs for the Active_Profile with their key metrics.
7. WHEN no Training_Plan exists for the Active_Profile, THE Dashboard SHALL display a prompt to create a new plan.

### Requirement 10: Pace and Heart Rate Zone Calculator

**User Story:** As a user, I want the app to calculate and display my personalised pace and heart rate zones, so that I can train at the correct intensity.

#### Acceptance Criteria

1. THE App SHALL calculate five Pace_Zones (Easy, Moderate, Threshold, VO2 Max, Anaerobic) in min/km based on the Active_Profile's recent race performance or estimated fitness.
2. THE App SHALL calculate five Heart_Rate_Zones based on the Active_Profile's maximum heart rate or age-predicted maximum heart rate.
3. WHEN the User provides a recent race result, THE App SHALL recalculate all Pace_Zones for the Active_Profile using an established formula (e.g., Jack Daniels VDOT).
4. THE App SHALL display all Pace_Zones and Heart_Rate_Zones for the Active_Profile in a dedicated zones screen with plain-language descriptions of each zone's purpose.
5. WHEN Pace_Zones are updated for the Active_Profile, THE App SHALL apply the new zones to all future Workouts in that Profile's active Training_Plan.

### Requirement 11: Notifications and Reminders

**User Story:** As a user, I want to receive reminders for upcoming workouts, so that I don't miss scheduled training sessions.

#### Acceptance Criteria

1. THE App SHALL support browser-based push notifications for workout reminders for each Profile independently.
2. WHEN a Workout is scheduled for the following day for a Profile, THE App SHALL send a reminder notification at that Profile's configured time (default: 20:00 local time).
3. THE App SHALL allow each Profile to independently enable or disable notifications and configure the reminder time from the settings screen.
4. WHEN the Active_Profile has not logged any Run for 3 consecutive days during an active Training_Plan, THE App SHALL send a motivational check-in notification for that Profile.

### Requirement 12: Settings and Configuration

**User Story:** As a user, I want to configure app preferences and manage integrations from a settings screen, so that the app behaves according to my preferences.

#### Acceptance Criteria

1. THE App SHALL provide a settings screen with sections for: Profile, Training Preferences, Strava Integration, and Notifications.
2. THE App SHALL allow the User to configure the Strava_Sync polling interval between 5 minutes and 60 minutes; this setting is shared across both Profiles.
3. THE App SHALL allow the User to export all Run data for the Active_Profile as a CSV file.
4. THE App SHALL allow the User to export the active Training_Plan for the Active_Profile as a PDF or iCal file.

### Requirement 13: Docker Deployment on Raspberry Pi

**User Story:** As a user, I want the app to run reliably in Docker on my Raspberry Pi, so that it is always available on my home network with minimal maintenance.

#### Acceptance Criteria

1. THE App SHALL be packaged as a Docker Compose configuration with all required services (web server, database, background worker).
2. THE Docker_Container SHALL support ARM64 architecture to run natively on Raspberry Pi 4 and later models.
3. THE App SHALL persist all data in a named Docker volume so that data survives container restarts and image updates.
4. WHEN the Docker_Container starts, THE App SHALL complete initialisation and be ready to serve requests within 60 seconds.
5. THE App SHALL expose a health-check endpoint at `/health` that returns HTTP 200 when all services are operational.
6. THE App SHALL log application errors to a file within the Docker volume so that logs persist across container restarts.
7. THE Docker_Container SHALL consume no more than 1 GB of RAM during normal operation to remain within Raspberry Pi resource constraints.

### Requirement 14: Data Integrity and Backup

**User Story:** As a user, I want my training data to be safe and recoverable, so that I don't lose my history if something goes wrong.

#### Acceptance Criteria

1. THE App SHALL perform an automated daily backup of the database to a designated backup directory within the Docker volume.
2. THE App SHALL retain the 30 most recent daily backups and delete older backups automatically.
3. THE App SHALL provide a manual backup trigger from the settings screen.
4. WHEN a backup completes successfully, THE App SHALL record the backup timestamp and display it on the settings screen.
5. IF a backup operation fails, THEN THE App SHALL log the failure and display a warning on the settings screen.

### Requirement 15: Strava Bulk Data Import

**User Story:** As a user, I want to upload my Strava data export ZIP file during onboarding or from the settings screen, so that the app can import my full running history and calculate an accurate initial fitness baseline without manual data entry.

#### Acceptance Criteria

1. THE App SHALL accept a Strava data export ZIP file (produced by Strava's "Download your data" feature) uploaded per Profile via the onboarding flow or the settings screen; each Profile's bulk import is independent.
2. WHEN a Strava export ZIP is uploaded for a Profile, THE App SHALL parse the ZIP, extract all running activities from the activities CSV and/or GPX/FIT files contained within, and import each as a Run record for that Profile only.
3. WHEN a Strava export ZIP is processed for a Profile, THE App SHALL use the imported Run records to calculate the initial VDOT score and Pace_Zones in min/km for that Profile, replacing the need to manually enter current weekly mileage and longest recent run.
4. IF a Strava bulk import has been provided for a Profile, THEN the current weekly mileage and longest recent run fields in that Profile's onboarding form SHALL be optional rather than required.
5. WHEN a Strava export ZIP is re-uploaded for a Profile, THE App SHALL not create duplicate Run records for activities that have already been imported for that Profile (idempotent import based on Strava activity ID).
6. WHEN the import completes, THE App SHALL display a summary showing the number of activities imported, the number skipped as duplicates, and the calculated VDOT score and Pace_Zones in min/km.
7. IF the uploaded file is not a valid Strava export ZIP or contains no running activities, THEN THE App SHALL display a descriptive error message and not modify any existing data.

### Requirement 17: Garmin FIT File Workout Export

**User Story:** As a user with a Garmin Forerunner 970, I want to download any scheduled workout as a structured FIT file, so that I can load it onto my watch and follow the session with full step-by-step guidance.

#### Acceptance Criteria

1. WHEN the User opens a Workout detail screen, THE App SHALL display a "Download for Garmin" button that initiates a FIT_File download for that Workout.
2. WHEN the User requests a FIT_File export for a Workout, THE FIT_Exporter SHALL generate a valid FIT_File containing one `workout` message and one `wkt_step` message per WorkoutStep in the Workout.
3. THE FIT_Exporter SHALL map each WorkoutStep to a `wkt_step` message with the following fields: `wkt_step_name` (the step label), `duration_type` set to `distance`, `duration_distance` set to the step's `distance_metres`, `target_type` set to `speed` where a `pace_zone` is defined (with `custom_target_speed_low` and `custom_target_speed_high` derived from the pace zone boundaries in m/s), and `intensity` set to one of `active`, `rest`, `warmup`, or `cooldown` based on the step label.
4. WHERE a Workout contains interval repeat blocks, THE FIT_Exporter SHALL encode each repeat block as a FIT `wkt_step` message with `duration_type` set to `repeat_until_steps_cmplt`, referencing the correct `wkt_step_index` of the first step in the block and the configured repeat count.
5. WHERE a WorkoutStep has a `hr_zone` defined, THE FIT_Exporter SHALL include an `hr_zone` target in the corresponding `wkt_step` message in addition to any pace target.
6. WHEN the FIT_File is generated, THE App SHALL serve it as a file download with the filename `{workout_type}_{scheduled_date}.fit` (e.g., `interval_2026-05-10.fit`) and `Content-Type: application/octet-stream`.
7. THE App SHALL expose the FIT export at `GET /api/v1/workouts/{id}/export/fit` and SHALL return HTTP 404 if the Workout does not exist or does not belong to the requesting Profile.
8. BOTH Profiles SHALL be able to independently export their own Workouts as FIT_Files.
9. WHEN the FIT_File download completes, THE App SHALL display transfer instructions: "Connect your Forerunner 970 via USB → copy to the GARMIN/NEWFILES folder → eject → the workout will appear in your Training menu."
10. IF a WorkoutStep is missing a `distance_metres` value, THEN THE FIT_Exporter SHALL return HTTP 422 with a descriptive error identifying the incomplete step and SHALL NOT generate a partial FIT_File.

### Requirement 16: Multi-Profile Support

**User Story:** As a household with two runners, we want two independent profiles in the same app instance, so that each person has their own training plan, history, and Strava connection without needing separate devices or logins.

#### Acceptance Criteria

1. THE App SHALL support exactly two Profiles, each with a user-editable display name (default names: "Profile 1" and "Profile 2").
2. THE Dashboard SHALL display a profile switcher that allows the User to select the Active_Profile; switching Profiles requires no login or password.
3. WHEN the Active_Profile is switched, THE App SHALL immediately display all data (Training_Plan, Run history, statistics, Pace_Zones, Heart_Rate_Zones, Streak, personal records) belonging to the newly selected Profile.
4. THE App SHALL ensure that Run records, Training_Plans, Workouts, Race_Goals, Pace_Zones, Heart_Rate_Zones, Streaks, personal records, and notification settings belonging to one Profile are never displayed or modified in the context of the other Profile.
5. EACH Profile SHALL have its own independent Strava OAuth connection, allowing each Profile to connect a different Strava account.
6. EACH Profile SHALL be able to independently upload its own Strava bulk export ZIP; the imported Run records SHALL be associated exclusively with that Profile.
7. THE App SHALL store training preferences (e.g., preferred training days, long-run day) and notification time independently per Profile.
8. THE App SHALL share the following settings across both Profiles: Docker configuration, database backup settings, and Strava_Sync polling interval.
9. WHEN the User edits a Profile's display name, THE App SHALL update the name immediately in the profile switcher and throughout the UI.
10. IF the User attempts to delete or add a Profile beyond the fixed count of two, THEN THE App SHALL prevent the action and display an explanatory message.

### Requirement 18: Post-Run Analysis

**User Story:** As a user, I want to see a detailed comparison of my actual run against the scheduled workout targets, so that I can understand how well I executed the session and get actionable coaching feedback.

#### Acceptance Criteria

1. WHEN a Run is matched to a scheduled Workout, THE App SHALL display a post-run analysis screen showing: target distance vs actual distance in km, target Pace_Zone vs actual average pace in min/km, target Heart_Rate_Zone vs actual average HR (where available), and actual elevation gain in metres (where available).
2. THE App SHALL display a per-kilometre split table showing actual pace in min/km and actual HR for each km of the run (where GPS data is available from Strava).
3. THE App SHALL display a plain-language AI-generated summary via Gemini of how the run went relative to the target, including one actionable coaching observation.
4. WHEN the actual average pace falls within the target Pace_Zone, THE App SHALL highlight the pace comparison as "on target"; WHEN the actual average pace falls outside the target Pace_Zone, THE App SHALL indicate whether the run was faster or slower than target.
5. THE post-run analysis SHALL be accessible from the run detail screen and from the matched Workout detail screen.
6. THE post-run analysis SHALL be scoped to the Active_Profile.

### Requirement 19: Weather-Aware Coaching Notes

**User Story:** As a user, I want the app to factor in the weather forecast for my workout day and adjust the coaching note accordingly, so that I can prepare appropriately for the conditions.

#### Acceptance Criteria

1. THE App SHALL accept a home location (city name or latitude/longitude) in the settings screen, used for weather forecast lookups.
2. WHEN a Workout is scheduled within the next 7 days, THE App SHALL fetch a weather forecast for the workout date from the Open-Meteo API using the configured location.
3. WHEN the forecast temperature exceeds 25°C or humidity exceeds 80%, THE App SHALL append a heat/humidity advisory to the workout coaching note (e.g. "Start 10–15 sec/km slower than target pace and prioritise hydration").
4. WHEN the forecast indicates rain or wind above 30 km/h, THE App SHALL append a weather advisory to the coaching note.
5. IF the Open-Meteo API is unavailable or returns an error, THEN THE App SHALL display the coaching note without a weather advisory and SHALL NOT block the Workout from being displayed.
6. THE App SHALL cache the weather forecast per (location, date) for up to 3 hours to avoid excessive API calls.
7. THE App SHALL display the forecast temperature and conditions as a small badge on the Workout card in the calendar view and on the Workout detail screen.
8. THE weather feature SHALL be configurable per Profile — each Profile can set their own home location or disable weather advisories entirely.

### Requirement 20: Race Countdown

**User Story:** As a user, I want to see a countdown to my race on the dashboard when I have an active race goal, so that I stay motivated and aware of how much time I have to prepare.

#### Acceptance Criteria

1. WHEN the Active_Profile has an active Race_Goal, THE Dashboard SHALL display a race countdown widget showing the race name or label, the number of days remaining until the race date, and a short motivational message.
2. WHEN the Active_Profile has no active Race_Goal, THE Dashboard SHALL NOT display the race countdown widget — no prompt or placeholder is shown.
3. THE race countdown widget SHALL update automatically each day without requiring a page reload.
4. THE motivational message SHALL vary based on days remaining: more than 90 days ("Building your base"), 30–90 days ("Getting stronger"), 14–30 days ("Race prep mode"), 7–14 days ("Taper time — trust your training"), fewer than 7 days ("Race week — you're ready").
5. THE User SHALL be able to dismiss the race countdown widget for the current session without removing the Race_Goal.

### Requirement 21: GPX Route Suggestions

**User Story:** As a user, I want the app to suggest familiar routes from my Strava history when I open a workout, so that I can quickly choose a route that fits the session's distance and type.

#### Acceptance Criteria

1. THE App SHALL extract unique GPS routes from the Active_Profile's Strava-synced Run records that include GPS track data (polyline or GPX).
2. WHEN the User opens a Workout, THE App SHALL display up to 3 suggested routes from the Active_Profile's run history whose distance is within 20% of the Workout's target distance.
3. THE route suggestions SHALL be ranked by: (1) how often the Active_Profile has run that route for the same Workout type, (2) recency of last use.
4. EACH route suggestion SHALL display: a small map thumbnail rendered from the GPS polyline using a static map tile, the route's typical distance in km, and the number of times the Active_Profile has run it.
5. IF the Active_Profile has no Strava-synced Runs with GPS data, THEN THE App SHALL NOT display the route suggestions section.
6. THE route suggestions SHALL be scoped to the Active_Profile — routes from one Profile SHALL NOT appear for the other Profile.
7. THE App SHALL store extracted route polylines in the database to avoid re-parsing Strava data on every request.

### Requirement 22: Taper Calculator

**User Story:** As a user approaching my race, I want the app to automatically detect and display the taper phase with adjusted guidance, so that I know to reduce volume and trust my training in the final weeks.

#### Acceptance Criteria

1. WHEN a Training_Plan contains a Race_Goal and the current date is within 21 days of the Race_Goal date, THE App SHALL activate the taper phase display.
2. THE AI_Coach SHALL automatically include a Taper Training_Block as the final block of any Training_Plan that spans at least 8 weeks, with reduced volume (typically 20–40% reduction from peak week) and maintained intensity.
3. WHEN the taper phase is active, THE Dashboard SHALL display a "Taper Mode" indicator replacing the standard Training_Block name.
4. WHEN the taper phase is active, THE App SHALL display a taper guidance panel on the Dashboard with: current week's target mileage reduction percentage, a reminder to prioritise sleep and nutrition, and a note that feeling sluggish during taper is normal.
5. THE taper phase duration SHALL be configurable per Race_Goal: 1 week (5k/10k), 2 weeks (half marathon), or 3 weeks (marathon) — defaulting based on race distance.
6. WHEN the taper phase is active, THE AI_Coach SHALL NOT suggest plan adaptations that increase training volume, even if the User skips a Workout.
7. THE taper calculator SHALL be scoped to the Active_Profile's active Training_Plan and Race_Goal.

### Requirement 23: Data Export and Re-import

**User Story:** As a user, I want to export all my app data as a portable file and re-upload it to restore or analyse it, so that I have full control over my training data.

#### Acceptance Criteria

1. THE App SHALL provide an "Export All Data" option in the settings screen for each Profile that exports all data for that Profile as a single JSON file containing: profile data, all Run records, all Training_Plans and Workouts, pace zones, HR zones, race goals, and import history.
2. THE exported JSON file SHALL be human-readable and self-describing, with a `schema_version` field and an `exported_at` timestamp.
3. THE App SHALL provide an "Import Data" option in the settings screen that accepts a previously exported JSON file and restores all data for the Active_Profile from that file.
4. WHEN importing data, THE App SHALL validate the JSON file against the expected schema before making any changes; IF validation fails, THE App SHALL display a descriptive error and make no changes.
5. WHEN importing data, THE App SHALL ask the User to confirm whether to merge with existing data or replace it entirely; replacing SHALL delete all existing data for the Active_Profile before importing.
6. THE exported JSON file SHALL be suitable for external analysis (e.g. opening in Python/pandas or Excel via JSON import).
7. THE App SHALL expose the export at `GET /api/v1/profiles/{profile_id}/export/json` and the import at `POST /api/v1/profiles/{profile_id}/import/json`.
8. BOTH Profiles SHALL be able to independently export and import their own data.
